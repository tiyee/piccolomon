# 10 MiB 大文件性能检查

检查日期：2026-10-15。针对当前工作区，包括已有的未提交改造；本次没有修改生产代码或依赖版本。
新增独立的 `crates/ryne-session/examples/large-file-perf.rs` 作为复现入口。

## 结论

现有投影、控件和正文排版缓存值得保留，但不足以保证 10 MiB 文档流畅编辑。
优先消除源码映射、语义查询和排版中的重复扫描，再做可见区域排版与块级失效。
全文解析和 IME 全文临时解析是随后必须解决的输入路径成本。
文件字节数不是唯一规模指标：物理行数、语义块数、映射 span 数和嵌套深度都需要记录。

## 已确认的热点与建议

### 1. 源码映射的重复线性查询，优先级最高

`crates/ryne-projection/src/lib.rs` 的 `position_at()` 先遍历所有表格单元格，
再从头遍历所有 span；`source_at()` 同样存在全量查找。
`crates/ryne-features/src/presentation.rs` 为每个代码行、列表行、引用和 flow 块调用映射。
例如为每个段落创建 flow 时，起止位置各查一次。当块数 B 和 span 数 S 都随文档增长，
这部分达到 O(B × S)，大量带格式或 CRLF 换行的短段落也会触发，不只是表格等复杂 Markdown。
纯文本段落可能合并成一个 span，此时映射本身不呈平方增长，但下面的逐行 flow 查询仍存在。

建议：投影完成文字/span 输出后，一次建立 source/display 双向查询索引，
单点查询二分，按源码顺序批量转换时使用递增游标。
表格空单元格锚点、引用末尾空行及原子公式/图表单独建立边界索引；
不能用简单二分替换后丢掉同起点、隐藏标记和 affinity 的原有语义。

### 2. 光标操作仍有全文工作

`Display::snap()` 对全文 `grapheme_indices()` 做 `min_by_key()`，
即使 offset 很靠前仍遍历全文；`deletion_range()` 也从头寻找相邻 grapheme。
`presentation::active_window()` 每次选择都会生成全量表格、公式并遍历 AST。
`normalize_heading_caret()` 另行查询表格、代码块、列表行与标题。
源码模式的 `Planner::select()` 也会执行 active_window 查询。
缓存命中也有前置工作：内置 `presentation_key()` 的 `block_window()` 查询会检查围栏草稿，
其裸 CR 检测和 AST 查询仍扫描全文。因此命中投影缓存不等于整个刷新为 O(1)。

建议：每个不可变投影建立分块 grapheme 索引（含块间连续 grapheme 的上下文），
就近查找边界；为内联范围/祖先、标题和当前容器建立区间查询。
不要仅对 UTF-8 字符边界取整，也不要假设每个 span 的边缘一定是 grapheme 边缘。
源码模式可以按其显隐契约绕过无用的 Markdown 显隐查询。

### 3. 语义查询没有真正缓存，结构文档存在额外平方路径

`SemanticQuery` 当前是只读方法门面，方法仍每次构建 `Vec`。
`code_block::blocks()` 即使没有代码也创建全文物理行；每个代码块从物理行头部找首行，
并从尾部找闭合围栏；容器前缀查询还扫描全部 token。
`table::tables()` 每次构建物理行与全部列表项，再逐表格/逐行从头找物理行。
`list::rows()` 每个物理行扫描代码范围、所有条目及全部 token。
引用投影逐引用调用 `quote::at()` 检查末尾空行，这个查询又构建全文物理行、扫描 token/AST，
并调用完整 `list::items()`；引用前缀隐藏还对每个前缀查整个引用集合。
`parser::normalized()` 每次查询都检查裸 CR；存在裸 CR 时会新建并完整解析规范化视图。
`Registry::preview_inputs()` 在没有预览提供者时也提取所有代码块。

建议：按 ParseSnapshot 身份保留一份不可变 SemanticIndex，统一提供物理行起点、
按类型的节点、容器前缀 token、列表层级/行归属、表格与代码信息。
类型不存在时直接返回空切片；物理行与 token 用二分或顺序扫描定位。
全文源码模式应在进入列表/表格/引用等结构提取前短路；当前部分实现先构建全部结构再过滤，
使不显示结构的模式仍付出结构计算成本。代码高亮等该模式需要的能力另按其契约保留。
裸 CR 检测/语义视图每份源码计算一次，源码字节仍保持原样。
只缓存结果还不能消除首次构建的平方复杂度，索引构建本身也必须改成单次扫描或有界查询。

### 4. 全文排版和每帧装饰仍需处理

`TextLayout::build()` 排版全文，`FlowSpacing::enter()` 逐行调用线性的 `flow_at()`；
空行还扫描后续 flow，列表行和引用同样有逐行全量查询。
每个外层引用背景再扫描全部已排版行；每个粗体 span 检查全部表格表头。
`prepaint_frame()` 每帧为所有代码面板、单元格和列表项生成装饰与交互区域，
`paint.rs` 虽跳过屏幕外正文的实际文字绘制，仍遍历全文行；列表标签和面板未在生成时按视口裁剪。
`selection_quads()` 遍历所有视觉行，`LayoutKey::new()` 每帧重新收集所有控件预留宽度。

建议分两步：先为 flow、列表、引用、表头和 Y 坐标建立索引，并只生成可见装饰、选区与控件；
随后以语义块缓存文字排版，使用块高度/累计高度索引定位视口，只精排可见区域及预取范围。
修改一个块或改变它的标记显隐时只失效相关块，后续块更新累计高度。
跨行表格按行虚拟化；超长单段、单行代码也需要内部切片，不能仅虚拟化顶层块。
命中、IME、选区、菜单与滚动锚点必须使用同版本几何；未排版目标先排版再接受命中。

### 5. 输入、撤销与 IME 全文解析

`Planner::apply_edits()` 和会话 undo 每次都创建完整 `ParseSnapshot::with_math()`。
IME 的 `projection_state()` 先复制整份临时文本再解析，临时投影不进入现有缓存，
因此每次候选更新还会触发投影和排版。
文件打开已在后台读取并建立会话，初次投影及正文排版仍在 UI 路径。

建议：先合并一次 refresh 中重复语义计算，增加版本绑定、可取消的后台解析/投影任务，
结果只在完整身份匹配时接收。需要编辑决策的结构命令不能直接用过期 AST。
长期实现安全的块范围失效与增量解析；围栏、容器、Setext、列表、引用及引用式链接
可能影响相邻甚至远处结构，不能简单按修改行单独解析。
IME 优先复用不受影响块，预编辑保持会话临时状态，确认仍一次事务。
异步化能够保持窗口响应，但不能消除计算量，也不能仅靠防抖达到即时编辑。
现有解析包没有接入增量更新通路，本次不改变其 0.0.4 锁定版本。

### 6. 内存与平台范围转换，作为后续优化

投影当前为每个源码字节分配 `Style` 和隐藏标记；解析器还创建按字节的 token ownership ledger。
因此 10 MiB 源文件的临时内存远大于 10 MiB，另有新旧解析/投影和全文排版存活。
建议用有序区间事件合并样式和可见性，最终仍生成同一源码映射，而非逐字节 Style 数组。

`Source` 内部是 `Arc<str>`，普通 clone 不复制全文；真正的修改会复制文本，
`DocumentCore` 还保留保存基线。暂不建议先替换成 rope：应先用基准判断它占输入成本的比例，
且现有解析 API 接收连续文本，单独换存储仍可能在解析前重新拼接全文。

UI 输入回调的 `editable_text()` 即使没有预编辑也返回整份 String，
UTF-16 范围转换和选区查询从文本起点扫描。建议无预编辑时借用不可变源码，
有预编辑时用临时分段视图；建立行级/分块 UTF-8 ↔ UTF-16 累计索引。
dirty 当前比较保存基线和全文文本，同长度末尾修改会遍历大部分内容，但应排在主要平方路径之后。

## 建议实施顺序与验收

1. 源码映射索引、grapheme 索引、SemanticIndex 和类型不存在时的快速路径。
   保持现有全量结果作为对照，验证所有边界语义。
2. 消除 flow/列表/引用/表格的重复查找，按视口生成装饰与选区。
3. 块级投影/排版缓存、可见区域排版、累计高度和滚动锚点。
4. IME 局部临时投影、版本化后台任务，再设计增量语义更新。
5. 区间样式构建与文本存储调整，根据剩余耗时和内存决定。

每阶段应重新测量：1/5/10 MiB 的打开到首帧、开头/中间/末尾输入和删除、连续导航、
滚动、显隐切换、跨块选区、粘贴与撤销、中文 IME 更新及确认。
语料需包括短段落、超长单段、嵌套列表/引用、大表格、单个长代码块和大量小代码块，
并包含 LF/CRLF/CR、组合音符、emoji/ZWJ 与文档末尾空结构。
记录 P50/P95/P99、峰值 RSS、行/块/span 数和实际主线程耗时；少量诊断样本不能作为尾延迟保证。

正确性门槛沿用源码唯一真相、原始换行保存、一次事务撤销、IME 确认不重复结构命令，
以及旧帧不得解释新源码。优化不以禁用块结构呈现代替需求。

## 基准与验证记录

环境：本机 x86_64 macOS、Intel Core i7-8750H 2.20 GHz、6 个物理核心、32 GiB 内存，
Rust 1.99.0。使用 `--locked --release`，无窗口，运行时没有并行基准或后台编译。
大小按 MiB 计算，重复完整语料单元，因此实际字节数略高于目标；10 MiB 普通段落为
10,485,774 字节（约 19.4 万段落，38.8 万语义节点）。

普通段落与长单行每项 3 个样本，无预热；以下为中位数，单位 ms。
构造/解析/投影返回值的析构在独立测量计时之外；输入发布会包含替换旧状态的正常成本。

| 操作 | 普通段落 1 MiB | 普通段落 10 MiB | 长单行 10 MiB |
| --- | ---: | ---: | ---: |
| 全文解析 | 65.03 | 667.70 | 253.93 |
| 末尾输入一个字节，含提交、不含投影 | 101.83 | 1087.03 | 403.30 |
| 撤销 | 91.63 | 1002.57 | 340.31 |
| 完整投影 | 61.55 | 608.19 | 458.94 |
| 已缓存投影返回，含 key 查询 | 0.81 | 11.25 | 7.30 |
| 末尾选择，不含 refresh | 6.93 | 69.62 | 34.00 |
| 光标规范化，不含 refresh | 17.94 | 207.31 | 123.15 |
| `Display::snap()` | 25.76 | 246.04 | 237.69 |
| IME 临时文本与全文解析，不含投影 | 64.52 | 681.63 | 285.81 |
| 源码模式投影 | 57.80 | 583.80 | 472.55 |

10 MiB 普通段落的源码事务准备为约 20 ms（本次另一轮约 28 ms），远小于完整输入路径；
普通段落的投影只有一个 span，不能用它代表带格式、多映射区间的最坏情况。
缓存控件引用返回低于 0.001 ms，但完整控件生成、refresh 和帧内区域构建另有成本。
各环节样本不能直接相加当作真实窗口端到端延迟。

大量块的增长趋势另用 64/128/256 KiB 诊断，每项一个样本，不作 P95/P99 推断，
也不把这些数值外推为已测过 10 MiB 结构文档：

| 语料/操作 | 64 KiB | 128 KiB | 256 KiB |
| --- | ---: | ---: | ---: |
| 带粗体和行内代码的短段落，完整投影 | 11.33 | 33.40 | 121.91 |
| 嵌套列表，完整投影 | 223.97 | 875.63 | 4425.53 |
| 嵌套列表，列表行查询 | 172.34 | 657.79 | 3480.34 |
| 嵌套列表，末尾光标规范化 | 165.08 | 644.87 | 3462.23 |
| 大量小代码块，完整投影 | 87.28 | 339.26 | 1386.38 |
| 大量小代码块，代码块查询 | 35.89 | 143.81 | 524.97 |
| 大量小表格，完整投影 | 77.79 | 296.63 | 1511.41 |
| 大量独立引用，完整投影 | 487.70 | 2470.05 | 10267.92 |

256 KiB 嵌套列表在全文源码模式下投影也耗时 3504.42 ms。
这些结果与前面的重复扫描路径一致：先缓存、索引和消除交叉扫描的收益优先于仅更换文本存储。

换行对照：1 MiB CRLF 普通段落的完整投影为 1516.27 ms（一个诊断样本），
生成 56,175 个 span；LF 普通段落为 61.55 ms（3 样本中位数），只有一个 span。
CRLF → LF 的展示映射会在换行处拆分 span，随后逐块线性查询映射的成本被放大。
两者总字节数接近但段落数略有差异，这个比值只是诊断对照，不能作为稳定加速倍数。
优化必须保留原始 CRLF，不能通过全文件转换换行格式规避成本。

`Style` 在当前构建中为 12 字节，10 MiB 源码仅逐字节样式数组就约 120 MiB，
还不含隐藏掩码、解析 AST、临时文本与 GUI 几何。`/usr/bin/time -l` 测得整组
普通段落进程峰值 RSS 约 773.8 MiB，长单行进程约 341.3 MiB；
这包括基准持有的新旧源码/投影和临时解析，不能当作实际 GUI 的内存测量。
