## 新发现

### N1 · P2 · 列表范围计算仍有列表数 × 代码块数的扫描

位置：[list_actions.rs:36](../../../crates/ryne-features/src/list_actions.rs#L36)。
`ListActions::controls` 为每个条目调用 `Extents::get`。该函数倒序检查末尾候选行，
每行均用 `self.code.iter().any(...)` 从头判断是否位于代码块。把上下文共享到批次级
避免了重复构建，但没有消除这个内层扫描。

复现语料：N 个带续行和空行的列表条目，后接 N 个围栏代码块。取当前生产函数的临时
副本，只在 `any` 谓词内插入原子计数，不改控制流，结果如下：

| 列表条目 | 代码块 | 代码范围谓词执行次数 |
| ---: | ---: | ---: |
| 100 | 100 | 20,000 |
| 200 | 200 | 80,000 |
| 400 | 400 | 320,000 |
| 800 | 800 | 1,280,000 |

这条路径在源码变化后生成控件时执行；执行单个列表动作还会重建该提供者的控件。
没有源码变化且贡献缓存命中时不会重复这批工作。以上是工作量证据，不是毫秒或 RSS。

建议：使用快照现有代码区间索引或有序范围二分判定，并借用快照的物理行/代码目录；
无列表时提前返回。不要改变尾部空行归属、嵌套前缀或代码内空行保留规则。验收包括
LF/CRLF/CR、列表内代码、嵌套子树、末尾空行以及混合语料的候选访问次数。

### N2 · P2 · 保存符号链接会替换链接本身

位置：[files.rs:37](../../../crates/ryne-services/src/files.rs#L37)。
读取通过 `read_to_string` 跟随链接，而保存直接把临时文件 rename 到传入路径，二者的
目标语义不一致。macOS 临时目录实测：`alias.md -> target.md` 打开内容为 `original`，
写入 `edited` 后返回成功；`alias.md` 已变为普通文件，`target.md` 仍是 `original`。
编辑内容没有丢失，但链接关系被静默破坏，依赖目标文件的其他工具看不到本次修改。

建议明确文件服务的目标身份策略：常规保存解析并绑定实际目标，在该目标的目录内
临时写入和原子替换；保留用户显示路径。对于链接重定向、悬空链接等变化，应重新检查
身份并给出明确结果。另存为的目标语义应单独定义。修复时不要简单改成原地覆盖，从而
丢掉现有原子保存能力。当前证据仅覆盖 Unix 符号链接，不外推 Windows junction 或硬链接。

## 既有问题的当前复核

### R1 · P2 · 历史恢复绕过普通发布验证

位置：[undo:452](../../../crates/ryne-session/src/lib.rs#L452)、
[普通验证:216](../../../crates/ryne-session/src/lib.rs#L216)。
普通编辑调用 validators 并检查 closers、显隐 Session；Undo/Redo 另走
`publish_history`，只部分检查规划结果。当前探针让验证器开始拒绝修改后，普通输入
被拒绝，Undo 和 Redo 仍改变源码，验证器新增调用 **0 次**。

这主要影响只读策略、动态约束和自定义命令扩展，并不证明内置撤销已损坏正常文档。
先定义 Edit/Undo/Redo 的策略：结构一致性始终检查，策略验证器显式声明是否限制历史，
历史不重跑输入补全。统一准备/验证/发布边界，拒绝时保持双栈、源码和会话状态，返回
可报告的错误，避免当前 `undo -> ()` 的静默失败。

### R5 · P2 · 控件动作变化与正文排版失效耦合

位置：[控件聚合](../../../crates/ryne-extensions/src/render_actions.rs#L131)、
[UI 接收:454](../../../crates/ryne-ui/src/lib.rs#L454)、
[LayoutKey](../../../crates/ryne-ui/src/text_layout.rs#L104)。
未声明缓存的提供者每次生成新分片，聚合 Arc 随之变化，UI 创建新的 ControlIndex，
该索引的 generation 直接进入正文 LayoutKey。即使返回完全相同的空列表，也触发这条链。
本次独立探针确认“连续两次空控件结果，聚合 Arc 不相同”；最终排版失效由代码链确认，
未为该扩展场景新增真实窗口构建次数探针。

建议分开表示正文度量、控件几何/目标、动作状态。仅 enabled/checked 变化应更新操作
状态；同宽换目标仍需更新控件映射。不能直接删除 generation 或复用旧 enabled。
几何索引中存有聚合数组下标，拆分时必须保证当前布局与当前控件批次仍一致。

### R6 · P2 · 投影命中缓存仍扫描全部预览候选

位置：[registry.rs:393](../../../crates/ryne-extensions/src/registry.rs#L393)、
[refresh:528](../../../crates/ryne-ui/src/lib.rs#L528)。
UI 在查询正文投影缓存前运行 `diagram_views`，注册表对每个代码块遍历贡献并调用
预览提供者。32 块限制约束成功候选数量，不限制大量“不适用”围栏的扫描。
本次探针：1,000 个普通围栏，10 次光标移动，正文缓存 **10/10 命中**，预览回调仍有
**10,000 次**。内置 FencedPreview 还会为真正匹配的候选提取正文。

建议预先整理预览提供者目录，增加适用语法及缓存依赖声明；源码候选与正文提取按
快照缓存，光标/选区/源码模式只做显示判定。对未声明依赖的提供者继续保守重算，
保持提供者与渲染器身份、故障隔离以及每文档图表限额。

### R7 · P2 · 实际高亮没有总预算，溢出工作集每轮同步重算

位置：[highlight.rs:272](../../../crates/ryne-services/src/highlight.rs#L272)、
[highlight:403](../../../crates/ryne-services/src/highlight.rs#L403)。
50 ms 和每轮八项限制属于语言识别，显式语言的 Tree-sitter 高亮直接同步执行。
本次重新运行计数探针：64/80/128 个不同 Rust 块的第二轮分别解析 **0/16/64 块**，
缓存均最多 64 项，`has_pending_work=false`。完整正文投影命中缓存时不会触发这轮重算；
编辑或显隐使投影重建时会再次支付成本。

建议为实际解析和高亮建立独立预算、任务身份及结果发布协议；先显示普通代码，优先
可见内容，保证未完成任务最终收敛。缓存需同时计算正文、spans 和相关资源的占用。
只扩大 64 项上限不能解决总工作预算与工作集抖动问题。

## 扩展性改进

以下是协议演进方向，除上文已计入项外，不再重复计为缺陷。

1. **按贡献冻结导出，而非按是否存在 additional 模块拒绝。**
   [MarkdownFeatures::snapshot](../../../crates/ryne-features/src/lib.rs#L78) 对任何 additional
   模块返回 None。本次空控件扩展也使纯文本 PDF 快照渲染被拒绝。可声明“不影响导出”、
   “可冻结呈现”和“无法冻结”；最后一种仍应明确拒绝，不能直接把现场可变服务送进后台。
2. **将装饰和菜单变成实际可组合的贡献。** `Slot::Decoration` 目前是声明，
   `BlockContribution` 在 features 内部；主呈现与 block-menu 独占，BlockCommand、
   InsertBlock 为封闭枚举。可优先开放有顺序和冲突规则的范围装饰、命令 ID 与菜单贡献，
   继续只有一份源码映射。出现具体新块需求后再扩展原语，无需预先建设动态插件 ABI。
3. **单目标动作使用目标级验证。**
   [RenderActionRegistry::plan](../../../crates/ryne-extensions/src/render_actions.rs#L366)
   为验证一个动作重建整个提供者的控件。增加按 target 查询当前动作可用性的接口，默认
   保留全量兼容实现；表格/列表提供者先迁移。必须继续核对文档身份、范围与 enabled。
4. **SemanticQuery 应逐步覆盖真实热点。** 当前 ParseSnapshot 的 Deref 仍允许跨层遍历
   AST，功能层也可以绕过已有索引重新扫描。N1 说明“建立索引”与“实际使用索引”要分开
   验收。先迁移热点与容器查询，不为形式上的封装一次性改写所有解析器类型。
5. **补齐可替换公式服务的 GUI 边界审计。**
   [refresh 的 set_font](../../../crates/ryne-ui/src/lib.rs#L474) 和
   [Assets::load 的 render_asset](../../../crates/ryne-ui/src/assets.rs#L67) 直接调用服务；
   它们不在 GuardedFeatureEngine 的投影回调边界内。若未来替换公式服务，应统一保护并
   提供诊断与源码回退。本次未在 AppKit 中注入 panic，也未证明内置 Formulary 会因此崩溃。
6. **历史和控件需要内存账目。** core undo/redo 没有条数或字节预算；表格为每个单元格
   生成完整动作 Vec，随后进入贡献缓存、聚合与 UI 索引的克隆。先记录逆向编辑、
   checkpoint、活动快照、控件和缓存的实际占用，再决定历史裁剪及共享动作描述，
   不凭对象个数宣称内存已经有界。

## 建议实施顺序

1. N1：沿用已有索引消除列表交叉扫描，回归现有范围语义；N2：独立处理文件目标身份。
2. R1：先明确历史验证策略，再统一发布验证，不将策略选择藏进重构。
3. R5/R6：拆开正文度量与控件动作失效，缓存预览候选，补真实窗口构建次数与命中计数。
4. R7：单独实现高亮预算/调度与生命周期；再推进按贡献导出和目标级动作查询。
5. 以上完成后再推进大文件 P3：块级布局复用、可见块精排与高度索引；保守局部语义和
   IME 投影仍属于 P4/P5。当前编辑、IME 临时态和新布局仍有全文工作，已有视口绘制
   不能等同端到端大文件支持。

性能验收应使用独立 release 语料：普通段落、多小围栏、长代码、长表格、嵌套容器、
密集公式；覆盖首中尾编辑、导航、滚动、IME、LF/CRLF/CR。记录输入到显示的
p50/p95/p99、分阶段耗时、布局重建次数、缓存命中、重复解析数和峰值 RSS。
本次工作量探针与 debug 冒烟日志不能据此推算最大文件大小或具体提速比例。
